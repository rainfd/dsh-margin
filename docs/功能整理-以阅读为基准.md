# 重新整理：以「阅读」为基准的功能归位

**日期：** 2026-10-08
**基准变更：** 上一版按「8 域 / 47 项」等权重拆分，错误。本项目的目的是**阅读**——
采集与格式化都是为了让阅读舒服。据此重排。
**实测环境：** Margin 生产 `8.134.185.171:3000`，232 篇候选（未读 88 / 已读 144）；
DSH `packages/` 源码；dsh-margin `cbd298b`。

---

## 0. 先把目标写成一条流水线

```
资料进来 → 采集 → 格式化成文章 → 【阅读】 → 笔记 → 入库
   ↑                                  ↑
   Margin 负责前半                 断在这里
```

这条链上每一步「方便」与否，才是功能整理的正确坐标系。

---

## 1. 现状体检：逐段打分

| 段 | 能力 | 现状 | 判定 |
|---|---|---|---|
| 1 资料进来 | URL 导入 / RSS / 微信 / 知乎 / PDF | Margin 全有；RSS **生产在跑**（5 源 / 360 分钟 / 4 个 active job，实测） | ✅ 好 |
| 2 采集 | 正文抽取、Cookie 注入、无头兜底 | `url_ingest_service` + 3 个 extractor（2,000+ 行） | ✅ 好 |
| 3 格式化成文章 | 三态产出 `content_html` / `content_text` / `content_md` | **实测：`content_md` 是干净 markdown 且保真** | ✅ 好 |
| 4 **阅读** | 打开一篇文章 | **DSH 面板只给原始网页外链，把格式化好的正文丢掉了** | ❌ **最大断点** |
| 5 笔记 | 划线、批注 | DSH 侧无 | ❌ 无 |
| 6 入库 | 存 Trilium / 建任务卡 | DSH 侧无；Margin 有存文章但**建任务卡 0 命中** | ❌ 无 |

**核心结论：你的系统前半段（1–3）做得很好，后半段（4–6）在 DSH 里是断的。
而第 4 步断得最可惜——文章已经格式化好了，插件却把它扔掉只给一个链接。**

### 证据

```
1) 字段丢弃：API 返回 20 字段 → toCandidate 只留 14 个
   被丢：content_html, content_text, content_md, content_fetch_failed, ...
2) 唯一动作：ReadingList.tsx:151  window.open(candidate.sourceUrl, '_blank')
   → 点开是 martinfowler.com，不是 Margin 格式化后的正文
3) 实测延迟：单篇正文往返 54ms，正文 3.5KB —— 拿了就能直接渲染，没有性能借口
```

## 2. 问题一：有没有更简化的方法？

**有，而且比上一版估计的简单得多。原因是三个实测发现：**

### 发现 1：`content_md` 是干净 markdown，保真

```
抽样 30 篇：缺 content_md 0 篇；含图 13 篇，md 丢图 0 篇
结构覆盖（21 篇）：代码块 6 | 表格 2 | LaTeX 3 | 原生标题 3
```

html/md 的元素计数一致（链接 14/14、15/15），图片以 `![](https://...)` 保留。

**这意味着上一版列的「必须引 DOMPurify + CSP 才能渲染 `content_html`」整个问题消失了**——
渲染 markdown 不需要 sanitizer。

### 发现 2：DSH 已有现成的 markdown 渲染器，且插件已白名单

`MarkdownText`（`packages/client/ui-primitives/src/markdown/MarkdownText.tsx:174`）自带：
GFM、代码块（shiki）、KaTeX、表格、脚注、**远程图片**（`remoteImageUrl` 允许 http/https：`render.tsx:70`）、
`streaming` 模式、图片灯箱。

而且 **`@deepseek-ai/dsh-client-ui-primitives` 已经在插件的 `tsdown.config.ts:29` externals 白名单里**——
**零新增依赖即可使用**。

### 发现 3：`tool.call.toolview` 让「阅读」不必新建任何界面

该 slot `{kind:'keyed', scope:'session'}`，**按工具 wire name 分发**：
`{name:'tool.call.toolview', key:'margin_get_candidate'}`（范式见 `ui-skill/src/client/index.ts:81-84`）。
`props.block` 提供本次调用的结果数据（`slots.ts:98-104`）。

### 于是有三层方案，从简到全

| | 方案 | 新增界面 | 阅读在哪 | 笔记在哪 |
|---|---|---|---|---|
| **A** | **工具卡渲染文章** | **0 个** | **对话里** | **直接对 agent 说** |
| B | `main` 全局面板（列表→阅读两页） | 1 个主面板 | 独立页面 | 面板内 |
| C | 会话级右侧 Tab（真多标签） | 1 个 tab 类型 | 右侧栏 | 右侧栏 |

**建议先做 A，理由不是省钱，是它更符合你的实际动作：**

1. **零导航基建。** DSH 没有 URL 路由（全库 grep `pushState`/`hashchange` 零命中），
   「页面」是根 store 里的一个 keyed 值。方案 A 完全不需要这些。
2. **阅读与笔记同处一屏。** 你的目标原话是「方便我阅读，也方便后续做笔记」。
   在对话里读，读到一半直接说「这段记一下」——笔记和入库都是 agent 的天然动作。
   分成两个界面反而要来回切。
3. **阅读位置天然持久。** 会话日志本身就是存储，transcript 记住了你读到哪篇。
4. **失败成本低。** 一个 toolview 组件 ≈ 100 行；A 验证完再决定要不要 B。

**A 长什么样：**

```
你：我有什么待读的
agent：margin_list_candidates → 88 条（列表卡）
你：打开 862
agent：margin_get_candidate(862)
       ┌─────────────────────────────┐
       │ 片段：10月4日                │   ← toolview 渲染 content_md
       │ Martin Fowler               │      MarkdownText，可滚动
       │ ─────────────────────────── │
       │ 针对我的上一篇片段……         │
       │ > 我们部署了本我，却忘了超我  │
       └─────────────────────────────┘
你：这篇读完了，顺便把结论记一下
agent：margin_mark_read(862) + 建 Trilium 任务/笔记   ← 第 5、6 段一次做完
```

**方案 A 同时修好了第 4、5、6 段，且不动任何现有界面。**

## 3. 问题二：已读/未读的存储

### 3.1 先看现状（实测）

| 维度 | Margin 现状 | 缺口 |
|---|---|---|
| 文章正文 | ✅ 三态 + `toc_json` | — |
| 已读/未读 | ✅ `Candidate.status`（`unprocessed`/`read`） | — |
| **何时读的** | ❌ **无 `read_at` 字段**（实测 grep 零命中） | **缺** |
| **读到哪了** | ❌ 全系统无（前端只有 sessionStorage 存"最后打开哪篇"） | **缺** |
| 笔记/高亮 | ✅ 独立表 | 与渲染管线耦合（见 §4） |
| 阅读来源 | — | 未区分"在 DSH 读的"与"在 Margin 读的" |

### 3.2 体量实测（决定存储策略的关键数字）

```
全库 232 篇（未读 88 / 已读 144）
平均每篇：md 21KB | html 32KB | text 17KB   （UTF-8 实测）
全库推算：md 3.9MB | html 5.9MB | 三态合计 12.9MB
若只把 markdown 读进内存：188 篇 ≈ 2.2MB
```

**2.2 MB —— 整个阅读库的 markdown 比一张手机照片还小。**

这直接改变了存储问题的性质：**不需要分页、不需要虚拟滚动、不需要增量同步框架。**
上一版担心的「规模不匹配」不存在。

### 3.3 存储设计：单一真源 + 增量维度

```
┌─────────────────────────────────────────────┐
│ Margin = 内容真源 + 阅读状态真源              │
│   content_md / 三态正文     ← 内容的唯一归属  │
│   Candidate.status          ← 已读/未读唯一归属│
└─────────────────────────────────────────────┘
                    ↕  只走工具，不双写
┌─────────────────────────────────────────────┐
│ DSH = 阅读进度的增量存储（ctx.storageDomain）  │
│   readAt        何时读的（Margin 没有）        │
│   position      读到哪了（全系统没有）         │
│   source        'dsh' | 'margin'（在哪读的）  │
└─────────────────────────────────────────────┘
```

**为什么这样分：**

1. **已读/未读只能有一个写入方。** `reconciliation-rules.md` 已经因为双写踩过坑
   （「重复 `taskStatus` + 跨实例 `marginCandidateId` 错配」）。
   `status` 留在 Margin，DSH 只通过 `margin_mark_read` 写——**一处写，一处读**。

2. **DSH 存的是 Margin 根本没有的字段**，所以它不是第二真源，是**增量**。
   这避免了"两套系统都说自己知道读没读"的经典冲突。

3. **状态口径要区分。** `reconciliation-rules.md:43` 明确「自动对账不可根据 Margin 的未读 toggle 重开任务」，
   第 61 行进一步要求「设为 `read`（不是 toggle）」。建议：
   - Margin `status` 继续做**业务状态**（供对账、digest 用）
   - DSH 的 `readAt` 做**阅读事实**（供「本周读了什么」「继续阅读」用）

### 3.4 读取策略：一次拉取 + 本地缓存

**为什么不走"每开一篇请求一次"：**

```
实测：列表 100 条 109ms | 单篇正文 54ms
全量预热 232 篇 × 54ms ≈ 12.5s（一次性，放 ctx.jobs 后台跑）
预热后：打开任意一篇 = 0 往返
```

**推荐：懒加载 + LRU。**

- 打开时取一次，存 DSH 侧缓存（`ctx.storageDomain`，zod 校验，`storage-sqlite` 后端可用）
- 缓存上限按 50 篇 ≈ 1MB，超了淘汰最旧
- 「继续阅读」列表从缓存读，秒开
- 后台预热只在你在 DSH 里开始阅读后才触发（不必默认开启）

**注意：** profile 当前**未启用任何 storage bundle**（实测 `~/.dsh/profiles/web/package.json` 无 storage 条目）。
需要加 `@deepseek-ai/dsh-storage-sqlite`（或 json）到 bundles。这是一个前置动作。

### 3.5 已读文章堆积怎么办

144 篇已读，且在持续增长。这是**信息架构问题，不是存储问题**（总量才 2.2MB）。建议：

- **默认视图只显示未读**（88 条）——已有此默认，保持
- 已读按**时间倒序**、可搜索，不做删除
- 真正的清理应由**入库**解决：读完 → 结论进 Trilium → Margin 侧标记
- `reconciliation-rules.md` 已明确「`done` 是终态，不回退」，与此一致

## 6. 仍然存在的一个硬约束

**高亮 offset 与渲染管线强耦合**（上一版结论不变）：

服务端按 `len(content_text)` 校验 offset（`highlights_router.py:53-93`），客户端用可见文本 TreeWalker 截取
（`textSelection.ts:52`），指纹在浏览器算，且存在「KaTeX 必须先完成」的顺序不变量（`EditorialReader.tsx:163-170`）。

**但注意：这个约束现在影响面小多了。** 因为方案 A 不改渲染方式的话——
`MarkdownText` 渲染 markdown 与 Margin 渲染 HTML 的**可见文本不同**（实测 content_md 比 content_text 长 1.33–1.65 倍，
含标记符号），所以在 DSH 里做的高亮**不能直接回写 Margin**。

**阶段 A/B 先不做高亮，笔记走「对 agent 说」的路径**（结论文本存 Trilium，不依赖 offset）。
这既绕开了耦合，也更符合「方便做笔记」。
